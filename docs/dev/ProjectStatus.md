# Project Status

Where the project stands, the decisions behind it, and what's left to do. Update this file when one of these changes.

_Last updated: 2026-10-16 (docs restructure on branch `docs/readme-restructure`, see To Do. Earlier, unreleased: PS1 options row, PowerShell 5.1 or 7 and `-File` or `-Command`. ## Goal

Make it easy to run MSI and EXE installers (and scripts) as SYSTEM to test installs the way ConfigMgr and Intune run them, without downloading PsExec and running it from the right folder. Pick an installer, type the arguments, click Run.

## Decisions Made (and Why)

| Topic | Decision | Reason |
| --- | --- | --- |
| Look and structure | Match [GetMSIInformation](https://github.com/MichaelEscamilla/GetMSIInformation) and [CodeSigningTool](https://github.com/MichaelEscamilla/CodeSigningTool): one `.ps1` file with WPF, the same palette, update check, right-click menu and `iex (irm …)` launch | Keeps the tool family consistent |
| PowerShell version | Works in Windows PowerShell **5.1** (the baseline) and PowerShell 7, with no step that switches to pwsh when it's installed. The elevation and update relaunches use the PowerShell the script is already running in (`$Script:CurrentPowerShellPath`, from `$PSHOME`), so starting it from pwsh stays in pwsh (2026-10-10). `.ps1` installers use 5.1 by default, with PowerShell 7 as an option (see "PS1 options"). The right-click menu uses pwsh 7.4+ if it's installed when the menu is installed, otherwise 5.1 (2026-10-10, matching GetMSIInformation) | Testing often happens on devices that don't have PowerShell 7. GetMSIInformation prefers pwsh 7.4+ wherever it's installed. RunAsSystem only stays in the PowerShell it was given, so 5.1 users are never moved to pwsh and pwsh users are never dropped to 5.1 |
| How it runs as SYSTEM | A one-time Scheduled Task (Session 0) by default, based on the [Patch My PC Connectivity tool](https://github.com/PatchMyPCTeam/CustomerTroubleshooting/tree/Release/PowerShell/Connectivity) | Avoids PsExec, and Session 0 is how ConfigMgr and Intune really run installers |
| Interactive mode | Optional PsExec mode (`-s -i`) | Lets you see the installer's UI. If PsExec isn't found, the tool offers to download it from live.sysinternals.com into `%LOCALAPPDATA%\RunAsSystem\PsExec` (`$Script:PsExecFolderPath`). Lookup is that folder, then the PATH. The PATH is checked folder by folder with `[IO.File]::Exists`, not with `Get-Command`, which took about 1 s per name in 5.1 and made switching to Interactive (and typing in that mode) lag when PsExec wasn't downloaded yet (fixed 2026-10-14). Changed 2026-10-14 from the installer's folder, which wrote PsExec into System32 or a PowerShell folder for a tool and into shares |
| Other PsExec options | **Not done** (2026-10-14). Non-interactive PsExec (`-s` without `-i`) was considered and rejected. So were `-d` (no exit code, breaks Stop), `-x` (Winlogon desktop, too niche) and `-h`/`-l` (irrelevant with `-s`). A session picker for `-i` (UI in the console session while on RDP, or the other way round) is the only one worth revisiting, and only if someone needs it | Without `-i`, the process runs in Session 0 with no window, which Session 0 mode already does the way ConfigMgr and Intune do (real exit code, stdout capture). The PsExec client is started hidden, so its relayed output would go nowhere, and console tools with no arguments would hang waiting for input |
| File types | `.msi`, `.msp`, `.exe`, `.ps1`, `.cmd`, `.bat`, `.vbs` | MSI and EXE are the main use; scripts were requested too |
| MSI options | An action choice (Install `/i`, Uninstall `/x`, Repair `/fvomus`), a UI level, and `/l*v` | Requested |
| `/norestart` checkbox | **Removed** (2026-10-09) | The owner doesn't use it. Type `/norestart` in ArgumentList when it's needed. Older history entries still contain a `NoRestart` field, which is now ignored |
| MSI log name | `<installer file name>.<Action>.log` next to the installer: `Setup.msi.Install.log`, `.Uninstall.log`, `.Repair.log`, or `Update.msp.Patch.log` for an MSP (changed 2026-10-09, it was `Setup.msi.log`). Changing the action updates the name only if the box still holds the automatic name (`$Script:DefaultLogPath`). A typed path is kept, and a new file always gets a new default. History entries keep the log path they were run with | Owner's request, so the logs from install, uninstall and repair of one MSI don't overwrite each other |
| Working directory | The installer's own folder | Matches ConfigMgr and Intune |
| Copy to a local cache first | **Not done** | The owner said it wasn't needed |
| Current user mode | Added 2026-10-09 as a third run mode (`CurrentUser`). It runs as **the account running the script**, with the script's elevation (in practice elevated), on that user's desktop. It uses the same `Register-SystemTask` with principal parameters: the script account's SID, `LogonType` 3 (interactive token) and `RunLevel` 1 or 0. The option shows the account and its elevation, and the Run button reads "Run as Current User" | Owner's choice to start simple and test before deciding further. Using the scheduled task (instead of `Start-Process`) keeps the exit code, cleanup, Stop and history shared, so later variations only change the principal |
| Current user variations considered | **Not done yet**, to be decided after lab testing: (1) running as the user signed in to the window's session instead of the script account (`WTSQuerySessionInformation`), which handles an admin elevating with a different account; (2) forcing no elevation (`RunLevel` 0) to match Intune and ConfigMgr user context; (3) warning when that user has more than one session, because Task Scheduler picks the user, not the session, so UI could appear in the other session | Discussed 2026-10-09. Each one only changes the task principal or adds a check before the run |
| Stop button | Added 2026-10-09. A red **Stop** button (`btn_Stop`) appears next to Run during a run. It uses the same label and the same confirmation prompt for every file type, and the prompt explains the MSI behaviour. `Get-RunProcessId` finds the process by the installer path in its command line, started after the run began, skipping this app and the local PsExec client. `taskkill /T /F` then ends that process and its whole tree. After that it stops the scheduled task or the PsExec client, in case the search missed something. The run is recorded as **Stopped** (category `Stopped`, grey). Only the text underneath differs for MSI and MSP ("Stopped waiting - Windows Installer is still running the install..."). Pre-release builds wrote `Cancelled` and `StoppedWaiting`, and those still display as Stopped | Stopping the task only ends the process it launched directly, and killing PsExec only ends the local client, so bootstrapper and PSADT children kept running. One label and one prompt was the owner's preference: the action is the same whatever the file type. Stop is a separate button so that double-clicking Run can't stop anything. The Windows Installer service is never matched, because its command line doesn't contain the installer path |
| Really stopping an MSI | **Not done** (2026-10-09). Lab testing showed the install carried on after it was stopped. The `msiexec.exe /i` client exits, but the Windows Installer service (`msiexec /V`) keeps running the install. The options considered were: stopping the service, rejected because it affects every MSI install on the device and can leave a half-applied install; and a clean cancel through the MSI API's UI callback (rolls back, exit `1602`), rejected because it needs a SYSTEM-side host process instead of running `msiexec.exe` directly | The owner is fine with a warning: stopping an MSI partway through is part of testing, and you can uninstall afterwards |
| Timeout | **Not done** | The owner said it wasn't needed. Use Stop instead |
| 32-bit (Intune-style) launch | **Done for `.ps1` only** (2026-10-14), as a choice in the PS1 options. Not for other file types | The owner first said it wasn't needed, then asked for it for scripts |
| Detection-rule help (new Uninstall registry entries) | **Not now** | Possible later |
| History | `%LOCALAPPDATA%\RunAsSystem\History.json`, last 50 runs, with Load, Copy and Clear | It saves locally even when the script is launched with `iex` |
| ArgumentList label | The arguments box is labelled **ArgumentList** for every file type. It used to switch between "Properties" and "Arguments". Internal names (`txt_Arguments`, `-Arguments`, the history `Arguments` field) are unchanged | Owner's preference. Leaving the internal names alone keeps old history files and `-Arguments` callers working |
| Changing the file | If the new file is the same type, all options are kept. If the type is different, everything except the path goes back to the defaults: Install, Silent, log on, ArgumentList empty, Session 0. Only known types are compared, so a half-typed path doesn't clear anything | Settings for one type rarely suit another, for example MSI properties passed to an EXE |
| Remembering choices between launches | **Not done** | History already restores a whole run, and remembered choices would conflict with resetting to the defaults when the file type changes |
| Section cards and colours | Each section (Installer and options, Run As, Command Line, Result, History) is a `Card` border with its header inside (`CardHeader`), 10px/6px padding and a `BorderMuted` outline. File and options share one card with a thin divider, which leaves the command line about 97px; separate cards left only about 68px. The window background is a new token, `Window` (`#231915`): the darkest stone mixed with a little of the site's darkest orange. Cards are `Bg`, inputs `Surface`, buttons `Surface2` | The owner wanted clearer sections. Card fills of `Surface` with inputs in `Bg` made the inputs look like holes to the window, and an orange outline was too loud. Giving each layer its own shade fixed it. The palette matches michaeltheadmin.com (Blowfish stone and orange). **`Window` isn't in GetMSIInformation or CodeSigningTool yet**, so add it there to keep the family consistent |
| Main form layout | The ArgumentList box wraps and grows from one line up to about three (76px), then scrolls. Enter still doesn't add a line break. The result panel is a fixed 118px, and the command line takes whatever height is left (scrolling if needed). The copy button stretches to the same height as the command line box | The command line is the part that changes length, so it gets the leftover space. The result panel always holds the same content |
| File box shows the end | When a path is loaded (Browse, drag and drop, Tools, history, `-FilePath`) or the box loses focus, the File box scrolls to the end of the path (`Show-FilePathEnd`), queued at `Loaded` priority because the box hasn't measured new text yet. On focus loss it's skipped while the box has keyboard focus, so typing isn't disturbed. Loaded paths go through `Set-FilePath`, which forces it, because a drop doesn't move focus and the box is often still focused (Reset focuses it). Added 2026-10-14; the owner confirmed it works for loaded files in 5.1 and pwsh 7 the same day | A long path was cut off on the right, hiding the file name, which is the part that matters |
| Open Log during a run | Open Log is pointed at the new run when it starts, so it never opens the previous run's log. Open Log is hidden until the log file exists, then shown while the install is still running (`Watch-SystemRun` checks on its 500 ms tick, one `Test-Path` per tick until the file appears). It opens with the default app for `.log` files. The logging switch stays `/l*v` | The owner wanted to watch an MSI install while it runs. A specific viewer such as CMTrace isn't installed in a known place, and someone using Notepad can close and reopen the file. Before this, Open Log kept pointing at the previous run's log during a new run. A log panel inside the app was considered and turned down |
| Capturing stdout and stderr | Added in 2026.10.12.0. Only **Session 0** runs of EXE, PS1, CMD/BAT and VBS are captured (`Test-CaptureOutput`). For those, the task's action is a Windows PowerShell `-EncodedCommand` launcher (`Get-OutputCaptureCommand`) instead of the installer. It starts the installer with `System.Diagnostics.Process` (arguments passed through exactly as typed), copies stdout and stderr into one file as they're written, and exits with the installer's exit code. The file is `%LOCALAPPDATA%\RunAsSystem\Output\<task name>.txt`; the newest 50 are kept, and the history entry stores its path (`OutputPath`). It's shown on a **Stdout line** under the run details (`txtblk_Stdout`): `Stdout: <latest line>`, one line cut off with "...", in Consolas, coloured `Accent` and underlined in `AccentHover` on hover so it reads as a link. During the run it follows the file on the 500 ms tick, re-reading only when the file has grown, and only its last 4 KB (`Get-OutputLastLine`, OEM code page, split on CR too so progress lines show their latest state). After the run it keeps the last line. Clicking it opens the whole file. It's hidden when nothing was written. The line is labelled `Stdout:` even when that line came from stderr, because both go into one file. There's no Open Output button (decided 2026-10-12; a 2x2 button grid was tried and dropped) | Session 0 is the only mode where the output is lost: PsExec and Current user show the console window, and redirecting there would hide prompts such as `pause`. msiexec writes nothing to stdout, so MSI and MSP still run directly. The task can't redirect output itself, which is why this is the one exception to "the action is the installer". `-EncodedCommand` keeps the installer path out of the launcher's command line, so Stop still finds and ends the installer. `Start-Process` was avoided because it treats `[` `]` in paths as wildcards |
| ArgumentList variables | Added in 2026.10.13.0. `{LogFile}` (`<installer path>.log`, no action in the name because the app can't tell what an EXE is doing), `{InstallerDir}` (the installer's folder, no trailing backslash, so `{InstallerDir}\x.log` also works at a drive root) and `{InstallerName}` (file name **with** its extension). They're filled in by `Get-CommandSpec` (`Get-ArgumentTokenValues`, `Expand-ArgumentTokens`), only for those exact names and case-insensitive, so MSI product codes in braces are left alone. The box and history keep the tokens; the Command Line box and the history command line show the values. A line under ArgumentList (`Insert: {LogFile} {InstallerDir} {InstallerName}`, link-style `LinkText`) inserts at the cursor, or at the end if the box wasn't in use; each token's tooltip shows its value for the loaded file, and the `{LogFile}` one says it's only a path, not a way to make the installer log. **Copy arguments** (right end of that line, shown when there are arguments) copies the arguments with the values filled in. When `{LogFile}` is in the arguments, Open Log uses that path, unless an MSI's `/l*v` log is on, which takes priority. A path built from `{InstallerDir}` and `{InstallerName}` isn't followed by Open Log | The owner had to add a log switch to an EXE by hand, and every vendor's switch differs. Tokens instead of pasting real paths, so a history entry or another file of the same type gets its own path, and Open Log knows the exact path instead of guessing it from free-form arguments. The name `{LogFile}` was chosen over `{LogPath}` (clashes with the MSI log box), `{DefaultLog}` and `{SuggestedLog}`; the tooltip carries the "helper only" caveat. The `Installer` prefix (not `File`) keeps the pair consistent and avoids a generic `{FileName}` an installer might use itself. The extension stays in `{InstallerName}` so a product with both an EXE and an MSI installer keeps its logs apart (the owner's choice). A `{Timestamp}` token was tried and **removed**: with nothing else to build a file name from it was awkward, and it can come back now that `{InstallerDir}` exists. `%Name%` syntax was avoided because Task Scheduler and cmd expand it themselves (as SYSTEM, `%TEMP%` is `C:\Windows\Temp`) |
| PS1 options | Added 2026-10-14 (unreleased). Two rows shown only for `.ps1` files (`panel_Ps1Options`). **PowerShell** (`cmb_Ps1Host`): Windows PowerShell 5.1 (default), Windows PowerShell 5.1 (32-bit) (`$Script:WindowsPowerShell32Path`, SysWOW64; disabled on a 32-bit OS) or PowerShell 7. PowerShell 7 is only offered for a machine-wide install (`$Script:PwshPath`: `%ProgramFiles%\PowerShell\7\pwsh.exe`, else `pwsh.exe` on the PATH outside WindowsApps and the user profile, which SYSTEM can't reach); otherwise the item is disabled and reads "not installed". A history entry that used an unavailable host loads as 5.1. **Passed as** (`cmb_Ps1Invoke`): `-File` (default), `-Command` or `-EncodedCommand`. The items are just the switch names; better descriptions are still to be decided. Its tooltip is a plain string, because the `ToolTip` style shows content as text and an element would show its type name. `-Command` runs `& { & '<script>' <ArgumentList>; exit $LASTEXITCODE }` (`Get-Ps1CommandText`), wrapped in double quotes for the Windows command line rules (`ConvertTo-NativeArgument`: `"` becomes `\"`, backslashes doubled only before a quote). `-EncodedCommand` runs the same code as base64 UTF-16LE. The rows follow the order the command is built in (the owner's request): PowerShell and ExecutionPolicy, then Parameters and Passed as. **ExecutionPolicy** (`cmb_Ps1Policy`): Bypass (default), Unrestricted, RemoteSigned, AllSigned, or Not set (tag `Default`: the switch is left out, so the device's policy applies). **Parameters** (`txt_Ps1Parameters`): free text placed after `-NoProfile` and `-ExecutionPolicy`, before `-File`, `-Command` or `-EncodedCommand`. All four are saved in history (`Ps1Host`, `Ps1Invoke`, `Ps1Policy`, `Ps1Parameters`; missing means the defaults), non-default choices are shown on the entry's second line, and they reset when the file type changes. When the path isn't in the command line as is, Stop finds the process by `Spec.ProcessMatch`: the path with `'` doubled for `-Command`, the base64 text for `-EncodedCommand` | Under `-File` Windows splits the ArgumentList, not PowerShell: `-Path 'a','b'` isn't an array, single quotes don't group, and a path with spaces in single quotes breaks into positional arguments (`PositionalParameterNotFound`). This came up passing several folders to a Patch My PC folder script. `-Command` lets PowerShell parse the ArgumentList; `-EncodedCommand` also avoids every quoting rule on the way, PsExec included. The 32-bit host reproduces Intune scripts that run in a 32-bit PowerShell, where the registry and Program Files are redirected. The policy choice tests whether a script would be blocked under a real policy (unsigned or downloaded scripts). `-NonInteractive` was considered as its own checkbox and turned down; it can go in Parameters. A script's own `exit N` sets `$LASTEXITCODE`, so its code comes through. A try/catch around the call (so a bad parameter gives exit 1) was tried and **removed** at the owner's request (2026-10-14). `-File` stays the default. Tested outside the app on 2026-10-14 in 5.1 and pwsh 7, through `Get-CommandSpec`: arrays, double quotes with a trailing backslash, `''` in single quotes, `exit 3010`, a throw (exit 1), 32-bit (`Is64BitProcess` false), pwsh with `-EncodedCommand`, a chosen policy, Not set picking up the device policy, and `-NonInteractive` in Parameters, with the script in a folder named `dir [x] it's`. An offscreen render shows both rows fit |
| Tools | Added 2026-10-14 (unreleased). An arrow button beside Browse (`MenuItem_Tools`, a one-item `Menu` with the `SplitArrowHeader` template, so the title bar menu styles reach its items; a `ContextMenu` sits outside the window's tree) opens a list that fills File with Windows PowerShell 5.1, 5.1 (32-bit), PowerShell 7 (hidden when not installed) or Command Prompt. Any EXE in System32, SysWOW64 or a PowerShell program folder counts as a tool (`Test-IsTool`), so Browse to `whoami.exe` behaves the same. For a tool: the working directory is `$Script:ToolWorkingDirectory` (`C:\Windows\Temp`) instead of its folder, `{LogFile}` and `{InstallerDir}` point there too, the file info line reads "Tool, Working directory: ...", it counts as its own type for the options reset, and PsExec is looked for and downloaded in `C:\Windows\Temp`. Running powershell.exe, pwsh.exe or cmd.exe in Session 0 with no built arguments asks first (checked on `Spec.Arguments`, so `-Command ""` doesn't count): Yes switches to Interactive (PsExec), No runs anyway, Cancel. Stop only matches a tool's processes that descend from the Task Scheduler service or `PSEXESVC.exe` (walking parents, with a start-time check against reused PIDs). **PowerShell tools** (powershell.exe or pwsh.exe, `Test-IsPowerShellTool`) show the PowerShell options panel, which `Update-Ps1Options`/`Set-Ps1OptionsLayout` adapt: the PowerShell host row is hidden (the tool is the host) and ExecutionPolicy, Parameters and Passed as fill the gap, still in command order. Passed as is **As typed** (default; the ArgumentList goes to the tool unchanged, like any EXE, and ExecutionPolicy and Parameters grey out because you write the whole line), **-Command** (the ArgumentList is the code, and `-NoProfile`, the policy and the parameters are added) or **-EncodedCommand** (the same, base64). The policy label shortens to "Policy" in the narrow column. `Get-PowerShellInvocation` builds the `-Command`/`-EncodedCommand` arguments and the Stop match string, shared with the `.ps1` branch. cmd.exe and other tools get no panel | A Tools menu in the title bar was tried first and moved beside Browse at the owner's request: picking a tool is another way of choosing the file, and the arrow takes no height from the command line. Variables in the File box (`{PowerShell}`) were considered and turned down: File, type detection, Open Folder and history all expect a real path, and the system paths are the same on every device. A tool's path isn't unique to a run like an installer's, so without the ancestry check Stop could end a PowerShell window you opened during the run. Installers keep the old matching, so a child left behind by a parent that exited is still found. Session 0 runs are useful for checking what SYSTEM sees (network, proxy, certificates) with output capture; PsExec gives a SYSTEM console. Tested outside the app on 2026-10-14: `Test-IsTool` (ccmcache and other folders aren't tools), the spec's working directory and token values, and a task's program being a child of the Schedule service's svchost |
| Result buttons | The Result section has at most one button, **Open Log**, and it's only shown when it can be used: an MSI or MSP run with logging on, or any run with `{LogFile}` in its arguments, once the log file exists (during the run or after it). If the log was never written, for example a run that failed early, it stays hidden. **Open Folder** moved out of Result into the File box as a folder icon beside the reset icon (`btn_OpenFolder`). It opens the folder of the file in the File box and is shown whenever that file exists, before or after a run (2026-10-12) | The owner preferred showing a button only when it does something, over a disabled one. Open Folder always opened the installer's folder, so it belongs with the file, not the result. Before this it was only enabled after a run |
| Result when the file changes | The result, Open Log and the Stdout line belong to the file that was run (`$Script:ResultFilePath`). Loading a different file clears them (`Clear-RunResult`, also used by Reset). Loading the same file again keeps them | The owner noticed that a stopped run's result stayed on screen after a new file was loaded, which made it look like the result of the new file |
| Exit code display | The decimal code is shown large, with its hex value always shown in small text underneath. The console log includes both | EXE installers often document their codes in hex, and HRESULTs are easier to look up that way |
| Copying the exit code | Click the decimal code or the hex value to copy just that value (`Copy-ExitCode`). The hand cursor and "Click to copy" tooltip only appear when a real code is shown, not for `--`, `...`, `Stopped` or `Error`. Both text blocks are left-aligned so only the text itself is clickable | The owner wanted the code easy to look up. No extra button, so the result panel keeps its fixed height |
| Status bar messages | `Set-StatusBar` shows a message, then one reused `DispatcherTimer` (`$Script:StatusTimer`) puts back `$Script:DefaultStatusBarText` after 4 seconds. A new message restarts the countdown. The restore state is kept on the timer's `Tag`. `-Persist` keeps a message until the next one or Reset; only the "Loaded run WITHOUT its arguments" warning uses it | Matches CodeSigningTool's `Set-StatusMessage`. The owner wanted resetting as the default, with a way to keep messages that ask you to do something |
| Reset | A ✕ icon inside the right end of the File box (`btn_Reset`), or `Ctrl+R`, runs `Reset-Form`. It puts the window back to how it opens: no file, default options, an empty log path, the result showing "Not run yet", Open Log, Open Folder and the Stdout line hidden, no history selection, and the default status bar text. History is kept. It's disabled during a run | The owner wanted a clean start without reopening the tool. Putting it inside the File box avoids adding a row under Browse |
| Keyboard shortcuts | `Ctrl+Enter` and `F5` run, `Ctrl+O` browses, `Ctrl+L` loads the selected history entry, `Ctrl+R` resets. They're handled in `PreviewKeyDown` on the window and only act when the matching button is enabled. The button tooltips list the shortcuts | Requested. Checking whether the button is enabled stops a shortcut from starting a second run or loading history during a run |
| Updating | Ported from GetMSIInformation `main` (2026-10-10). Clicking **Update Available** acts on how the script was launched (`Get-UpdateChannel`, worked out once at startup). The startup check is queued with `Dispatcher.InvokeAsync` at `ApplicationIdle`, so the window draws first (the same as GetMSIInformation). A PowerShell Gallery install is recognised by the `InstalledScriptInfosRunAsSystem_InstalledScriptInfo.xml` file next to the script, not by `Get-InstalledScript`, which held up the window by 4-6 s while it loaded PowerShellGet. **Web** (`iex`): opens the release page. **RightClick** or **LooseFile**: downloads `RunAsSystem.ps1` from the release tag to `%TEMP%`, checks that it parses, copies it over the running script, then relaunches it with the loaded file. **PSGallery**: runs `Update-Script`, then relaunches. When an update can't be applied (offline, locked, read-only or a parse error), it opens the release page instead. Updating is blocked during a run. The relaunch has no `-Verb RunAs` (the app is already elevated, so there's no UAC prompt) and carries `-FilePath` but not `-Arguments`. The right-click registry entry isn't rewritten | Matches GetMSIInformation. The parse check stops a truncated download or an error page from replacing a working script. The registry entry only points at the script path, so it doesn't change between versions |
| History entries | Each entry shows the file name and exit code, then the time, MSI action and mode, then the arguments on a third line (Consolas, cut off when too long). Load and Copy icon buttons appear beside the exit code only while the mouse is over the entry | Runs of the same installer with different arguments can be told apart, and loading a run takes one click. There's deliberately no "Run Again" button: you should load a run and review it before running it |
| History encryption | `Arguments` and `CommandLine` are saved encrypted with DPAPI (CurrentUser) as `ArgumentsProtected` and `CommandLineProtected`. Older plain-text files are encrypted the first time they're read. An entry that can't be decrypted (another account or device, or a password reset) is kept, and its arguments are left blank when it's loaded. The entry shows a red warning icon (the tooltip explains it), Copy is disabled, and loading it shows a red status bar message | Arguments can contain passwords and license keys, and they have to be saved so runs can be repeated quickly |
| Masking secrets on screen or in the console | **Not done** | The owner said it wasn't needed: typing a secret into the tool and sharing your screen are risks the user already understands. Copy uses the real command line |
| Drag and drop while elevated | Uses `WM_DROPFILES` with a message filter, plus Browse, paste and the right-click menu | The app has to run elevated, which normally blocks drag and drop from Explorer |
| Parameters | `-FilePath` and `-Arguments` | Needed by the right-click menu and handy for scripting |
| Name | RunAsSystem | The repo folder already used this name |

## Verified

Tested by the owner on 2026-10-09, elevated, in their lab on the devices the tool is meant for:

- Session 0 and PsExec modes with MSI, EXE and PS1 files. Arguments are passed through correctly.
- The app also works in PowerShell 7, although 5.1 is still the target.

Tested in Windows PowerShell 5.1 while building the tool (not elevated):

- The script parses in 5.1 and contains only ASCII characters.
- The XAML loads and the window renders (checked with an offscreen screenshot).
- The command line is built correctly for all seven file types and for PsExec mode.
- The MSI options panel shows and hides as expected, and the default log path is filled in.
- Exit codes get the right meaning and colour category.
- History saves, reloads, loads back into the form and clears.
- History encryption: values round-trip, a plain-text file is migrated, an entry that can't be decrypted keeps its encrypted value, and an empty history saves as `[]`.
- The elevated drag-and-drop hook compiles and attaches.

Output capture, tested outside the app on 2026-10-12 (not elevated), in 5.1 and pwsh 7.6:

## Known Limitations

- There's no timeout. An installer that waits for input in Session 0 runs until you click **Stop**.
- Current user mode runs with RunAsSystem's elevation (normally elevated), unlike Intune and ConfigMgr user context, which isn't elevated. It also runs as the account running the script, which may not be the user signed in to the desktop.
- Stop finds processes by the installer path in their command line. A child process that doesn't have the path in its command line is still stopped, because it's in the tree. A process the installer hands work to outside its tree is not stopped, for example a service it starts or an MSI it passes to the Windows Installer service.
- **An MSI can't be stopped.** Stop leaves Windows Installer finishing the install in the background, confirmed in the lab. The same applies to an EXE that runs an MSI internally. Starting another MSI before it finishes returns **1618** (another installation is in progress).
- PsExec rebuilds the argument list it passes on, so MSI properties with quoted values containing spaces may not reach msiexec exactly as typed. Session 0 mode passes them unchanged. The same may apply to a `.ps1` passed with `-Command`, whose whole command is one quoted argument with `\"` inside.
- With `-EncodedCommand` and output capture (Session 0), Windows PowerShell 5.1 writes stderr as CLIXML (`#< CLIXML`, then XML for errors, `Write-Host` and progress), so the output file and the Stdout line can show XML. No switch turns this off in 5.1. pwsh does the same unless `-OutputFormat Text` is in Parameters. The exit code isn't affected, and `-Command` writes plain text.
- With `-Command` or `-EncodedCommand`, a script that ends without `exit` returns the exit code of the last program it ran (`$LASTEXITCODE`), not 0 as with `-File`. A bad parameter or a missing script returns **0** (the error is only written to stderr, which the Stdout line shows in Session 0); a `throw` returns 1.
- `-Arguments` isn't passed on when the script relaunches itself as admin. Only `-FilePath` is.
- Captured output is saved as plain text in `%LOCALAPPDATA%\RunAsSystem\Output`, unlike history arguments, which are encrypted. A script that prints a secret leaves it there until it's one of more than 50 outputs. Clear History doesn't delete these files yet.
- Captured output is saved as the raw bytes the installer wrote. Console programs usually write in the OEM code page, so non-ASCII characters can look wrong in Notepad.
- With output capture, the installer's output goes to a pipe instead of a console. A few programs behave differently when they aren't writing to a console, for example by buffering output until they exit.
- Mapped drive letters aren't visible to elevated apps or to SYSTEM. The app tells the user to use the UNC path instead.

## Future Improvements

- A resizable window (currently 1100x760 with resizing turned off) that remembers its size and position.

- A filter box above the history list, to find a run by file name or argument.
- Pinned history entries that the 50-entry limit doesn't push out.

- A **"Don't save this run to history"** checkbox next to Run, plus a setting to turn history off completely, for arguments you'd rather not store even encrypted.
- Detection-rule helper: show the Uninstall registry entries an install adds, with the product code and uninstall string.
- More ArgumentList variables if wanted: `{Timestamp}` again (usable now as `{InstallerDir}\{InstallerName}-{Timestamp}.log`), and an Insert entry with common vendor log switches (WiX Burn `/log`, Inno Setup `/LOG=`, InstallShield `/v"/l*v ..."`). Open Log for EXEs is covered by `{LogFile}`; reading a path out of free-form arguments is no longer planned.
- An option to copy the installer to a local cache first, like ccmcache or the IME content folder.

- Cleaner captured output for `-Command` and `-EncodedCommand` runs. When a child `powershell.exe` has its error stream redirected (which Session 0 output capture does), Windows PowerShell 5.1 serializes that stream as CLIXML, so errors and `Write-Host` land as XML in the output file and on the Stdout line. There's no switch to turn it off in 5.1. The likely fix is `2>&1` in the wrapper (`Get-Ps1CommandText`), which folds the error stream into the success stream before PowerShell serializes it, so it comes through as plain text; a bare `throw` would still show XML unless a trap writes it as text first (which brings back the wrapping semantics the owner removed). Decoding on read was rejected as fragile, because stdout and stderr are interleaved into one file. Decided 2026-10-14 to leave as is for now.
